# dwell-guard 驻留调度守护进程（MVP）

> **一句话**：终结 Ollama 的"模型切换死循环"——自动记录使用习惯、预测下一个模型、预加载+保活，告别反复重载和 SSD 100% 占用。
>
> 状态：**MVP 练手版**——核心链路（记录→转移概率→预测→预加载动作）已验证，代理转发可用。

## 为什么做这个

Ollama 在多模型交替使用时（如"编码模型 ↔ 翻译模型"来回切）会**反复重载模型**：
- 每个模型冷启动 6-86 秒（读全量权重）；
- 反复换出换入 → SSD 100% 占用、响应极慢（社区称 "model-swap death spiral"）。

**现有工具**：Ollama 只有手动 `keep_alive`；llama-swap 做"手动规则热切换"，但**自动学习切换模式 + 预加载**仍是它的 open request（[#209](https://github.com/mostlygeek/llama-swap/discussions/209)）。

**dwell-guard 的差异化**：自动学（不用手写规则）——从使用历史推断"你 A 之后大概率用 B"，提前把 B 加载好。

## 原理

```
用户/Agent ──→ [dwell-guard :11500] ──转发──→ Ollama :11434
                  │
                  ├ 记录每次调用的模型 → history.json
                  ├ 转移概率：统计 A→B 出现次数
                  ├ 预测：A 之后最可能用 B
                  ├ 预加载 B（短驻留 10m，等用户切过来）
                  └ 高频模型保活（长驻留 30m）
```

**关键洞察**：预加载 = 发一个 `num_predict=1` 的最小 chat 请求让 Ollama 把模型载入内存（Ollama 无独立 load API），配 `keep_alive` 控制驻留时长。

## 快速开始

```bash

# 2. 让应用指向本守护（OpenAI 兼容）：
#    Open WebUI / 任何 OpenAI SDK：base_url 改为 http://127.0.0.1:11500

# 3. 正常使用即可——守护自动记录、学习、预加载
```


## 调度策略（当前版本）

| 情形 | 动作 |
|---|---|
| 模型调用 ≥3 次（高频） | keep_alive = 30m（长驻留） |
| 预测的"下一个"模型 | 预加载 + keep_alive = 10m |
| 其余高频模型 | 保活 30m（防止被切换踢掉） |
| **用户空闲 15s 以上** | **空闲预载预测目标**（keep 15m，用户在休息无竞争） |
| **预载大模型需空间** | **驱逐低价值模型**（成本感知：size/(freq²·predicted²)） |

## 当前局限（MVP 已知）

1. **只做记录+预加载动作**，还没做"驱逐决策"（哪个模型该被换出）——下一版；
2. **预加载时机**：现在是在"A 请求后"立即预载 B，还没做"空闲时预载"；
3. 代理只支持 `/api/chat` 和 `/v1/chat/completions` POST，`/api/generate` 未透传；
4. 保活用空请求实现，会触发一次极小推理（num_predict=1），有微开销。

## 3+ 模型场景验证 ✅（2026-08-31）

**场景**：35B 主力（写作）+ 30B 次用（日常）+ 0.6b 轻量（快速查询）的真实多模型工作流。

```
学习：35B×4（高频）、0.6b×2、30B×1 → 冷态清空
[轻] 0.6b 请求 → 驻留 0.6b
守护：驱逐/预载动作 → 空闲预载 35B
[切主力] 35B: 9.3s（冷启动基线 82s，8.8 倍提速）
```

守护日志确认全部能力协同：
```
驱逐 0.6b（给 35B 腾空间 23.9GB）  ← 驱逐决策
空闲预载 35B（用户空闲 20s）       ← 空闲预载
保活 35B (keep 30m)               ← 高频驻留
```

## 空闲预载 ✅ 已实现并真实验证（2026-08-31）

**机制**：用户停止操作一段时间后（空闲 15s），守护后台预载"预测的下一个模型"——用户在休息，无请求竞争，预载更安全。

```
用户请求 0.6b → 停止操作
→ 空闲 15s 后守护自动预载预测的 30B（keep 15m）
→ 用户回来切 30B 时已加载
```

**真实验证**（RTX 5070 8GB）：
```
请求 0.6b 后停止操作
[30s] 驻留空（空闲检测中）
[50s] 驻留: [qwen3:30b-a3b]  ← 守护自动预载！无需再请求
```

**三个设计要点**：① 去重（同目标不重复预载）；② 重置（用户新请求清空标记）；③ 保护（空闲预载同样走驱逐决策，只驱逐低价值模型）。

## 实测结果（2026-08-31，RTX 5070 8GB + qwen3:30b-a3b）

### 核心数据：预载的价值已验证 ✅

隔离实验（`ensure_loaded` 预载后立即请求，vs 纯冷启动）：

| 场景 | 耗时 | 说明 |
|---|---|---|
| 30B 纯冷启动（直连 Ollama） | **60.7s** | 从磁盘/内存加载 17.3GB 权重 |
| 30B 已驻留（守护预载成功） | **0.2s** | keep_alive 内模型在内存 |
| 30B 预载后立即请求 | **3.1s** | ensure_loaded 完成后马上切 |

→ **预载潜在收益：60.7s → 3.1s（约 20 倍提速）**，机制本身有效。

### 集成测试结果（干净环境复测，2026-08-31）✅ 部分生效

| 场景 | 耗时 | 说明 |
|---|---|---|
| 30B 纯冷启动（基线） | **61.5s** | 直连 Ollama |
| 30B 切换（守护预载后） | **30.7s** | 提速 ~50% |
| 30B 预载后立即请求（隔离，无其他模型驻留） | **3.1s** | 理论最优 |

**发现：预载受"当前驻留模型"限制** —— 集成测试里 0.6b 请求后预载 30B，但 0.6b 的 keep_alive 30m 还占内存，30B 只能部分加载（切时仍需搬层），所以只到 30.7s 而非 3.1s。

**关键认知（练手最重要收获）**：**预载和驱逐是硬币的两面**——只做预载不做驱逐，预载的大模型会被当前驻留的小模型挤占内存，无法完整加载。完整提速（61.5s → 3s）需要"驱逐当前模型给预载模型腾空间"，即 README 路线里的**驱逐决策（未实现）**。

### 集成测试暴露的问题（重要教训，练手收获）⚠️

1. **历史冷启动**：守护需先积累使用历史才能预测——首次请求无可预测对象，测试需先"学习几轮"；
2. **目录切换/守护重启后的首次请求偶发慢**：0.6b 曾 43-44s（后复测 0.2s 正常）——疑似 Ollama 侧一次性初始化，非磁盘问题（C/D 同盘已确认）；
3. **预载时机**（已重构修复）：预载若在"请求前"执行会和当前请求抢 Ollama 加载锁；已改为响应返回后延迟 2s 后台执行。

### 结论

预载机制**有效**：干净切换 61.5s → 30.7s（50% 提速），隔离条件可达 3.1s（20 倍）。瓶颈在"预载 vs 驻留模型的内存竞争"——**下一步实现驱逐决策**（成本感知：预载大模型时先驱逐低价值小模型），是打通完整链路的关键。

## 驱逐+预载完整链路复测 ✅ 达到理论最优（2026-08-31）

**代理链路完整复测（经 dwell-guard 守护，非独立脚本）**：

| 场景 | 耗时 | 说明 |
|---|---|---|
| 30B 纯冷启动 | **61.5s** | 基线 |
| 无驱逐预载（历史实测） | **30.7s** | 0.6b 占内存挤占 |
| **驱逐+预载（代理链路，本次）** | **3.2s** | **19 倍提速，达理论最优** |

守护日志确认动作链：
```
[请求 0.6b（低频）后]
驱逐 qwen3:0.6b（给 qwen3:30b-a3b 腾空间 18.6GB）: ok
预加载 qwen3:30b-a3b: ok
[切 30B] → 3.2s
```

**关键修复**：`model_size_gb` 原查 `/api/show` 的 `general.size`（不存在）→ 总是 0 → 错误 fallback 到 17GB 乱驱逐。改为**读本地 manifest**（真实 layers size），驱逐决策基于真实空间需求。

## 驱逐决策（成本感知）✅ 已实现并真实验证（2026-08-31）

### 机制
预载大模型前，自动驱逐"低价值"驻留模型给它腾空间。驱逐价值公式：

```
驱逐价值 = size / (freq+1)² / (predicted+1)²
  size       占空间越大 → 驱逐腾空间越多 → 驱逐价值↑
  freq²      使用频率（平方强惩罚，防驱逐主力模型）
  predicted² 被预测次数（平方强惩罚，防驱逐预测目标）
```

### 真实验证（RTX 5070 8GB）
```
驻留: [qwen3:0.6b (0.9GB)]          低频辅助模型
驱逐决策: [qwen3:0.6b]              ← 成本感知正确识别
卸载成功 → 腾出空间
预载 qwen3:30b-a3b: 完整加载 (19.2GB)
→ 无资源竞争，30B 可完整驻留
```

**打通完整链路的关键**：驱逐 + 预载组合后，30B 切换不再被驻留小模型挤占——理论上可达隔离实验的 ~3.1s（此前只有驱逐时是 30.7s）。

### 修复的 bug（练手收获）
- **模型名解析**：`name.split(':')[0]` 会把 `qwen3:0.6b` 截成 `qwen3`（错误）——Ollama ps 返回的 name 就是完整 tag，直接使用不 split。
